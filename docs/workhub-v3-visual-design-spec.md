# WorkHub V3 Visual Design Spec · Quiet Execution

状态：**正式视觉方向**。适用范围：WorkHub V3 的桌面页面及后续视觉迁移。本文是 UI 的视觉与信息层级 source of truth；[V3 部署执行基线](workhub-v3-deployment-plan.md) 继续约束产品模型、数据、业务行为及既有集成，[执行进度账本](workhub-v3-progress.md) 记录历史实施事实。本文不改变它们的业务边界，也不表示 Phase 8 已实施。

本规范从真实浏览器中的 [Quiet Execution FINAL](../artifacts/visual-direction-20260923/FINAL-quiet-execution.html)、[1440 整页](../artifacts/visual-direction-20260923/FINAL-1440-full.png)、[1920 整页](../artifacts/visual-direction-20260923/FINAL-1920-full.png) 和 [五方案对比](../artifacts/visual-direction-20260923/FINAL-COMPARE.html) 提炼。原生 Chromium 实测及限制见 [FINAL-REPORT](../artifacts/visual-direction-20260923/FINAL-REPORT.md)；当前产品现状来自 [真实浏览器审计](../artifacts/browser-audit-20260923/AUDIT.md)。原型仅有一个开放事项及一个待办行动，不能直接充当动态页面的 CSS、数据契约或多事项验收结果。

设计语汇：**安静、清晰、中高信息密度、PM 执行优先、适合长期高频使用**。用文字、对齐、空白和细分隔线建立层级；少卡片、少装饰。WorkHub 是个人软件项目经理工作台，不演化为 Jira、BI 大屏、企业后台、AI Inbox 或展示型 SaaS 页面。

## 1. Product Visual Principles

打开项目后，应先读到“项目现在在哪、有无风险、下一步推动什么”。当前待办、逾期/阻塞及行动责任人高于已完成记录、来源字段、历史事实和稳定项目资料。历史仍可完整访问，但默认占位应小。没有数据时明确写“暂无”，不造出健康判断、当前 STR、完成率或事项。

一个信息只给一个主要视觉位置。项目身份由标题承担，阶段/健康度以弱状态文字补充；同一字段不要同时出现在 kicker、徽标和元信息格。风险用短横排，执行用连续主列，阶段与 WBS 在次级区域，事实放在后段。长读区域保持一致起始线与可读行长。

内容本身有单一明确的操作焦点、需要在扫描时停留或危险确认时，才使用轻表面或 Card。普通元信息、计数、计划行、WBS gate、历史事实优先用 typography、divider、spacing 和 alignment。避免全屏等权模块、对齐不齐的圆角大卡、装饰性图标、英文全大写 eyebrow、没有语义的蓝色强调，以减少工程后台感和 AI 生成 UI 感。

## 2. Layout System

以下区间为设计约束，不要求机械复刻原型像素。**有效内容宽**不计侧栏，也不把主容器内边距算进可阅读区域。

| 布局部分 | 规则 | FINAL 的实测参考 |
|---|---|---|
| 桌面侧栏 | 安静、窄、当前项清楚；宽约 160–188px。只迁移外观，不增删现有一级导航或改变路由。 | 176px |
| 主阅读区 | 桌面有效最大宽约 1360–1480px。达到上限后居中，不把段落或表格强拉满 1920。 | 1920 下 1440px |
| 1440 | 导航外剩余空间应充分用于执行主列；内容外缘留约 24–40px，保证侧栏与内容呼吸感。 | 有效宽 1192px，导航后左留白 36px |
| 1920 | 内容可比 1440 更宽，但进入约 1360–1480px 的受控区间；两侧留白应对称、可解释。 | 有效宽 1440px，两侧各约 152px |
| 主/次级列 | 容器宽允许时两栏，去掉列间距后的主列约 68–74%，次级列约 26–32%；主列优先保证约 760px 可读宽，次级列约 320–360px，列间距约 32–48px。 | 1440 主列 796px，1920 主列 1032px |
| 内容内边距 | 桌面外层常规 24–36px；强调面内部约 16–24px；同层级标题共线。 | FINAL 主区约 36px |
| Section 节奏 | 4px 基础节奏；行内 8–16px，相关小组 16–24px，主要 section 24–32px；用边界与内容量决定间距，不靠固定高度撑满屏幕。 | 风险 y228，事项 y322 |

页面自然增长，不设置会截断内容的固定高度或 `overflow:hidden`。一个稀疏项目允许适度留白；若右栏导致主列尾部空段，应先减少重复内容和表格高度，再考虑改变两栏关系。风险与行动必须在阅读路径的前部，不能因为辅助栏或历史的高度被整体推迟。

## 3. Typography System

以下是跨页面的**语义字号 token**，实现时复用或调整现有 design system token 名，不把 FINAL 的 CSS 选择器复制到产品。中文与数字的实际字重、行高和换行必须在浏览器中检查。

| 语义 token | 桌面建议 | 用途 |
|---|---|---|
| Page title | 36–40px，项目 pilot 参考 38px / 约 1.15 行高，600 字重 | 一页一个强主标题 |
| WorkItem title | 22–24px，pilot 参考 24px / 约 1.4 | 执行主线的事项名称 |
| Section title | 主区 20px；次级区 18px；约 1.4 行高 | 连续阅读区段 |
| Action title | 18–20px，pilot 参考 19px / 约 1.5 | 具体待推进行动 |
| Body | 15px / 24px，常规 400 | 描述、事实、空状态正文 |
| Metadata | 14px；密集表头或辅助字段可 13px | 时间、负责人、来源、次要说明 |
| Caption | 13px 起，保持可辨对比度 | 注释、表格说明、展开入口旁注 |

标题数量与视觉强度反映信息层级，不能依靠满屏标签建立层级。11/12px 不能承载业务正文、日期、状态或重要操作。长标题允许自然换行，长 URL 使用安全换行，不能挤压日期列或造成横向滚动。数字采用等宽数字特性便于扫读。链接、按钮、展开控件保留可见焦点；状态除颜色外必须有文字。亮色与现有深色主题继续由各自语义 token 输出，不能因本原型只验证亮色而删除深色模式。

## 4. Color & Status

统一语义角色，再由主题映射具体色值。下表色值仅是已验证亮色原型的**起始参考**，不是跨页面强制逐像素复制；正式实现须检查深浅主题与正文/控件对比度。

| 角色 | 用法 | 亮色参考 |
|---|---|---|
| Canvas | 页面暖白底 | `#FDFDFA` |
| Surface | 有明确焦点的内容面 | 白色；行动强调可用 `#F6F5EE` |
| Sidebar surface | 比主画布略深，导航克制 | `#F1F3EE` |
| Divider | 细、连续、不过分围合 | `#DFE4DF` |
| Primary text | 标题与重要正文 | `#262E2C` |
| Secondary text | 描述与普通元信息 | 近似 `#536259` |
| Muted text | 来源、注释、日期标签 | 近似 `#68736D`，仍须可读 |
| Healthy | 真实健康状态 | 深绿文字 + 浅绿底，参考 `#496747` |
| Warning / P1 | 需要关注但未达到危险态 | 暖琥珀文字，参考 `#89602F` |
| Overdue / P0 / Blocked | 截止已过、最高优先级或阻塞 | 暖红文字，参考 `#A43F31`；分别写明“逾期 / P0 / 阻塞” |

状态色只表达数据中的状态。P0/P1 使用既有优先级语义，逾期按当前既有日期规则计算，blocked 按已有状态字段判断，健康度不替代风险汇总；不得按颜色自行推断新业务事实。正常/零值用主次文字，不给每个“0”上色。品牌蓝可用于现有可点击控件的必要辨认，不铺满卡片、图表或背景作为装饰。深色主题应保持相同的状态区分和可见焦点，使用语义映射调整明度与对比度。

## 5. Card Policy

Card 用于一个具有独立操作焦点的当前行动、需保持清楚边界的表单或确认、以及确需聚合的少量内容。项目 pilot 的单事项状态以 **1 个行动强调面**为参考，主要视觉 Card 以 **≤2 个**为 guardrail，Card 嵌套为 0。多行动场景不能每条都生成同等重量的大卡；主要行动突出，其余用平行列表、间隔和小标题组织。

项目页页框、section、计划表、风险数字、WBS gate、成员和链接摘要、历史事实都不是 Card 的默认理由。禁止“页面大卡 → section 卡 → 事项卡 → Action 卡”。需要连续信息时，优先用细 divider、适度空白、统一列线、轻背景；只有内容确实承担交互焦点时再围合。折叠不等于隐藏业务：默认摘要和进入完整内容的入口须同时可见。

## 6. Badge Policy

Badge 仅用于需要一眼识别的少量状态：priority、health、overdue、业务 state。一个实体的同一状态只标一次；项目代码、负责人、日期、来源系统、成员数量、STR 归属、计划日期使用文字或定义列表。若一行已有逾期文案，额外 Badge 只有在提高扫读速度时才增加。每行优先控制在 1–2 个重点 Badge，不能把所有元信息都药丸化；辅助状态可直接文字表达。

## 7. Button Hierarchy

| 层级 | 视觉与使用规则 |
|---|---|
| Primary | 当前页面最重要的可执行动作，常态下至多一个明显主按钮；例：表单保存。 |
| Secondary | 必要但非主路径的编辑、打开维护页、返回入口。 |
| Tertiary | 低干扰的筛选、视图切换、展开等局部操作。 |
| Danger | 删除等危险动作，保持危险语义、确认、加载和重复点击保护；不能伪装成普通主按钮。 |
| Text action | 列表“查看详情 / 查看全部 / 收起”等导航，保证可见且可键盘聚焦。 |

同页多个操作不得都用同等重量的主按钮。删除、编辑、保存及跳转反馈继续使用现有业务行为，不因视觉收敛而消失。控件有明确的 hover、focus、disabled、loading 和失败反馈。

## 8. Information Priority

项目详情正式优先级：

1. **Project identity / 当前状态**：名称、阶段/健康度、负责人与关键日期。
2. **Risk**：P0/P1、逾期、阻塞、红黄风险的真实摘要。
3. **WorkItem / Action**：当前开放事项、待办/逾期行动、负责人、截止及最近一句进展。
4. **STR / 阶段计划**：当前与下一 STR、日期和主要节点。
5. **WBS readiness**：当前门禁及其他 gate 的紧凑上下文。
6. **Recent Facts / history**：默认少量、可展开全部。

视觉顺序与语义顺序一致，但 STR 与 WBS 可作为同一首屏的次级栏；它们不得抢过风险和行动。项目当前 STR 来自已有 ProjectMilestone 选择逻辑，WBS 当前门禁来自 readiness，二者不能合并。当无明确当前 STR 时写“暂无明确当前 STR”，即使 WBS 门禁是 STR1 也不改写此事实。

## 9. Project Detail Reference Pattern

| 区域 | 设计职责 | 保留的信息与操作 |
|---|---|---|
| Header | 唯一 H1，短状态，紧凑元信息 | 项目名称、阶段/健康、负责人/PM、目标日期；编辑、删除及返回入口仍可找到 |
| Risk strip | 横向、低高度、零值降级 | 已有四类风险口径与具体数字；不做 KPI 大卡 |
| Open WorkItems | 主列按真实优先级展示 | 标题、状态、优先级、负责人、截止、真实 STR/项目级归属；进入全部事项与详情 |
| Action | 每个事项下清晰的待推进行动 | pending/逾期优先，标题、负责人、截止、最近进展；完整处理继续进入事项页 |
| STR / Plan | 次级列的紧凑计划 | 当前/下一 STR、主要节点与日期；完整维护入口可见 |
| WBS readiness | 计划旁的辅助执行信号 | 当前门禁、完成数/待交付和全部 gate 入口；不生成假事项 |
| Recent Facts | 后段连续事实行 | 默认 2–3 条，可看全部；日期、来源、内容及原日志跳转不丢 |

项目资料、链接、成员、长计划留在可发现的次级入口或折叠区域。描述只展示一次；已有 Action 数量、事项数量与风险数字如同时出现，要注明不同口径，不加总成新的总风险。对动态页面按实际数量自然撑开；FINAL 的单事项高度和具体文案只作 pilot 对照。项目级事项不因为页面布局靠近某 STR 就被自动归属。

## 10. Other Page Translation Principles

以下只定义设计原则，**不在本规范中重设计或承诺修改这些页面**。不增删当前正式产品的一级导航。

| 页面 | Quiet Execution 的映射原则 |
|---|---|
| 首页 `/` | 先呈现今日待推行动与需要关注的项目，再展示近期事实；项目卡突出真实当前/下一 STR，不增 KPI 墙。 |
| Today `/today` | 逾期与今日到期行动优先，已完成降级；保持行动到事项的清晰跳转。 |
| 项目列表 `/projects` | 根据实际条目数分配列宽，大屏卡片不应反而变窄；状态和下一行动可扫读。 |
| 事项列表 `/items` | 表格/列表承载相同语义，优先标题、状态、负责人、截止与行动进展；避免每行多层 Card。 |
| 事项详情 `/items/[id]` | Action → Timeline 连续阅读；右栏不重复头部 metadata，历史可完整访问。 |
| Reports `/reports` | 范围工具栏紧凑，管理摘要降级，真实项目→事项→行动→进展主线先于 Markdown 原文。 |
| Stats `/stats` | 已有统计保持辅助观察定位；图表按读数所需宽度布局，不为铺满大屏放大数据卡。 |
| Export `/export/*` | 导出正文保持可读行长，复制/导出操作清楚；少量内容留白可接受。 |
| Tools `/settings/tools` | 工具和模板按任务分组，表单宽度以操作可读性为准，不为填满视口拉宽。 |

## 11. Responsive Rules

正式验收优先桌面 **1440×1000、1920×1000**。侧栏保持克制；主执行列可以随可用宽度扩展，次级列仅在约 320–360px 可读范围内适度变化。描述、日志、导出正文保持阅读宽度，宽屏新增的是合理列宽与留白，不是把所有段落拉到视口边缘。

当侧栏、主列最小宽、次级列与间距不能同时满足时，布局转单栏：风险和执行先读，STR/WBS 随后，历史再后；不得强行压缩正文或出现横向滚动。断点由可用内容宽与文字换行决定，不把原型中的媒体查询值机械复用。窄桌面可缩小侧栏并把导航动作收敛，但不得丢操作。长标题、长 URL、多行 metadata、系统缩放 125% 应按内容自适应。移动端与深色主题未由 FINAL 原生双视窗证明，未来实现需另行验证，不能据此宣称已验收。

## 12. Anti-patterns

WorkHub 禁止下列视觉模式：

- KPI wall；将“0/1”做成一排占高大卡。
- Card 嵌套和每个 section 等权围框。
- 大面积渐变、玻璃效果、强阴影和大面积品牌色。
- 无意义图标、英文全大写装饰标签与密集 Badge。
- 大量 11/12px 业务正文或靠灰度过浅来“变安静”。
- 页面所有模块等权、历史事实压过当前行动。
- 1920px 下不受控地铺到近全屏。
- 为达到截图页高而截断、隐去、虚构或合并真实数据。
- 将 WBS gate 冒充当前 STR，将未归属事项按标题/日期推断进 STR。
- 视觉改造导致编辑、删除、跳转、展开、加载或错误反馈不可发现。

本规范的迁移顺序与验收约束见 [WorkHub V3 Visual Migration Plan](workhub-v3-visual-migration-plan.md)。
